什么是测试用例？

逐个字段构建一个测试用例，再对着真实的登录页面手工执行它。

学习成果

  • 说出测试用例的各个字段及其用途
  • 写出足够精确、任何人都能重复执行的测试用例
  • 手工执行测试用例并记录结果

要点

  • 一个测试用例只检查一个行为，并有 ID 和清晰的标题。
  • 前置条件、测试数据和测试步骤让它可以重复执行。
  • 执行前先确定预期结果，执行后记录实际结果。
  • 一个写明了精确实际结果的失败用例，已经是半份缺陷报告。

自测

  1. 哪个预期结果写得好？ 打开账户页面，标题为“欢迎回来，Ada”。. 它写出了可以观察、可以比对的东西。其他选项都会让两名测试人员得出不同的结论。
  2. 预期结果应该在什么时候写？ 执行测试之前. 如果事后再写，你往往会照着实际发生的情况去描述，缺陷就被当成“预期”放过去了。
  3. 第 1 步之前必须已经存在一个客户账户。这应该写在哪个字段？ 前置条件. 前置条件描述开始之前系统所处的状态。测试数据列出你要输入或发送的内容。
1.215 分钟▶ 1:53

好的测试用例与弱的测试用例

让测试用例值得信赖的五个习惯，以及许多团队采用的 Given、When、Then 写法。

学习成果

  • 发现测试用例中含糊的措辞并加以改写
  • 运用五个习惯：原子性、独立性、可重复、具体、可追溯
  • 用 Given、When、Then 的形式编写场景

要点

  • 用真实的值和可观察的结果代替含糊的措辞。
  • 让每个用例保持原子性、独立、可重复、具体、可追溯。
  • Given 是准备，When 是那一个操作，Then 是预期结果。

自测

  1. 某个标题写着“加入购物车并结账并使用优惠券”。它违反了哪个习惯？ 原子性. 一个用例包含三个行为，失败时你无法知道是哪一个出了问题。应该拆成三个用例。
  2. 用例 B 只有在用例 A 先执行并创建了订单时才能通过。应该怎么改？ B 在自己的前置条件中准备好所需的订单. 独立的用例可以按任意顺序执行，可以单独执行，也可以并行执行。B 应该自己创建需要的订单。
  3. 在 Given、When、Then 中，预期结果写在哪里？ Then. Given 是准备，When 是那一个操作，Then 是你期望观察到的结果。

设计测试用例

2.115 分钟▶ 1:25

等价类与边界值

等价类划分和边界值分析：用几个精心挑选的输入代替成千上万个。

学习成果

  • 把一个输入范围划分为若干等价类
  • 选出边界值及其相邻值
  • 把等价类和边界值转化为一组精简的测试用例

要点

  • 把软件应该同等对待的输入归为一组，每组测一个。
  • 缺陷往往聚集在边缘：测试每个边界值，以及紧挨着它的外侧值。
  • 差一错误（off-by-one）的比较，只有恰好落在边界上的值才能发现。

自测

  1. 某个字段接受 18 到 65 岁。哪组值覆盖了所有边界？ 17, 18, 65, 66. 每个边界加上紧挨着它的外侧值：下限是 17 和 18，上限是 65 和 66。
  2. 为什么一个等价类的中间只测一个值？ 软件应该以相同方式对待其中的每一个值. 这正是等价类的含义。如果 5 没问题，6 的表现几乎不可能不同。
  3. 代码写的是 qty < 10，但规则是 1 到 10。哪个测试能发现这个问题？ 数量 10. 只有恰好等于最大值的输入才会触发错误的比较。5、0 和 15 无论哪种写法，结果都一样。
2.215 分钟▶ 1:30

超越正常路径

反向用例、极端用例，以及用于组合规则的判定表。

学习成果

  • 列出输入出错的常见方式
  • 编写带有明确预期提示信息的反向用例
  • 构建判定表并发现需求中的遗漏

要点

  • 每条正常路径都有不顺利的“兄弟”：空值、格式错误、极端值、时机不对。
  • 反向用例检查软件能否得体地失败，并给出清晰的提示。
  • 判定表列出所有条件组合，暴露出没有被定义的情况。

自测

  1. 下面哪个是邮箱字段的反向用例？ ada.larkspur.test 显示“请输入有效的邮箱”. 它故意输入错误的数据，并检查软件是否清楚地拒绝它。
  2. 三个是/否条件组合在一起，完整的判定表最多有多少行？ 8. 每增加一个条件，组合数就翻一倍：2 × 2 × 2 = 8。其中有些行可以合并。
  3. 判定表中有一行没有定义结果。你应该怎么做？ 测试前先询问产品负责人. 这是需求中的遗漏。把它提出来，本身就是测试工作的一部分。
2.315 分钟▶ 2:06

Exploratory testing

Learn without a script: steer a time-boxed session with a charter, keep session notes, and turn what you find into test cases.

学习成果

  • Write a charter that gives an exploratory session one clear mission
  • Run a time-boxed session and keep notes someone else can read
  • Turn findings from a session into bugs, questions and new test cases

要点

  • Exploratory testing is designing and running tests at the same time, learning as you go.
  • A charter names a target, the resources you'll use and the information you want: one mission per session.
  • Session notes record what you covered, what you found and what you'd explore next, so the session can be reviewed.
  • Good findings become scripted test cases, so the next run doesn't depend on memory.

自测

  1. Which is the best charter for one exploratory session? Explore the discount code field with expired, misspelled and pasted codes to discover how errors are reported. It names a target, the resources (kinds of codes) and the information wanted. The others give no mission, so nobody can tell when the session is done or what it covered.
  2. Halfway through a session on the discount field, you notice the delivery estimate looks wrong. What should you do? Write it in your notes as an issue or follow-up idea, then return to the charter. The charter keeps the session focused. Noting the side issue means it isn't lost, and it can become the charter for a later session.
  3. Your session found that pasting a code with a trailing space rejects it. What should happen to that finding after the debrief? Report the bug, and add a scripted test case so the behaviour is checked on every run. Exploration finds the problem; a written test case keeps it found. Without one, catching a regression depends on someone happening to explore the same path again.

从测试用例到自动化测试

用 Arrange、Act、Assert 把写好的测试用例变成代码，看边界值测试抓住一个真实的缺陷。

学习成果

  • 把书面测试用例对应到 Arrange、Act、Assert
  • 用测试运行器编写单元测试
  • 先看到测试失败，再相信它的通过

要点

  • 测试名就是标题，Arrange 是准备，Act 是操作步骤，Assert 是预期结果。
  • 边界值测试能在几毫秒内让差一错误变红。
  • 先看到测试失败一次，再相信它的通过。

自测

  1. 自动化测试的哪一部分包含预期结果？ Assert. expect(...).toBe(...) 就是预期结果，由程序自动检查。
  2. 为什么要先看到新测试失败，再让它通过？ 为了证明这个测试能发现缺陷. 如果测试从来没有变红过，它检查的可能并不是你以为的东西。
  3. applyDiscount(20, "SAVE10") 返回了 20，但规则是满 $20 就打九折。最可能的缺陷是什么？ 用了 total <= 20 而不是 total < 20. 当 total <= 20 时提前返回，恰好 $20 的订单就拿不到折扣。边界值测试暴露了这个问题。
3.215 分钟▶ 1:46

组织测试套件

测试金字塔、需求追溯，以及如何让不断增长的测试套件保持健康。

学习成果

  • 用测试金字塔平衡测试套件
  • 把测试用例追溯到需求，找出遗漏和孤儿用例
  • 让测试套件保持健康：命名、不稳定的测试、责任归属

要点

  • 大量快速的单元测试，较少的集成测试，少数几个端到端测试。
  • 追溯矩阵能显示没有测试的需求，以及没有对应需求的测试。
  • 按行为给测试命名，并尽快修复不稳定的测试，否则大家会学会无视红色。

自测

  1. 大部分自动化测试应该位于测试金字塔的哪一层？ 单元测试. 单元测试快速而精确，所以构成宽阔的底座。
  2. 某个需求没有关联任何测试用例。这叫什么？ 遗漏. 这是覆盖上的遗漏。孤儿用例正好相反：没有对应需求的测试用例。
  3. 代码没有任何改动，某个测试却大约每十次执行失败一次。你应该怎么做？ 找到并修复原因，或者删除它. 不稳定的测试会侵蚀大家对整个测试套件的信任。修复原因（通常是时序或共享数据问题），或者删除这个测试。
