组织测试套件

测试金字塔、需求追溯，以及如何让不断增长的测试套件保持健康。

文字稿
  1. 引言
  3. 测试金字塔
  9. 需求追溯
  14. 保持健康
  19. 课程总结

学完本课你将能够

  • 用测试金字塔平衡测试套件
  • 把测试用例追溯到需求，找出遗漏和孤儿用例
  • 让测试套件保持健康：命名、不稳定的测试、责任归属

只有当大家信任测试套件、并且能在其中找到方向时，它才有用。把它塑造成金字塔，追溯到需求，并清除其中的噪音。

金字塔

  • 单元测试：一个函数或类，不涉及网络或数据库。毫秒级。数以百计。
  • 集成测试：几个真实的部件组合在一起，例如购物车和它的数据库。数量较少。
  • 端到端测试：像顾客一样通过浏览器操作整个应用。只有少数几个，用于关键流程。

把每项检查尽量放在最低的层级。第 2.1 课中的边界规则属于单元测试；“顾客可以买到一本书”则属于顶层。

追溯矩阵

维护一张“需求 → 测试用例”的表，或者给测试打上需求 ID 标签并自动生成这张表。检查它时关注两件事：没有用例的需求（遗漏），以及没有需求的用例（孤儿用例）。

保持健康

  • 命名： 描述行为。失败的测试名读起来应该像一个缺陷标题。
  • 不稳定的测试： 隔离只是最后手段；找到原因（时序、共享数据、顺序依赖）并修复它。
  • 责任归属： 需求变化时，相应的测试用例在同一个 pull request 中一起修改。
  • 精简： 删除与其他用例重复的用例，以及测试已移除功能的用例。
提示

下一步做什么。 选一个你负责的功能，写出它的追溯表，然后补上你发现的第一个遗漏。

检验理解 · 答对 2/3 即通过

1大部分自动化测试应该位于测试金字塔的哪一层？

单元测试快速而精确，所以构成宽阔的底座。

2某个需求没有关联任何测试用例。这叫什么？

这是覆盖上的遗漏。孤儿用例正好相反：没有对应需求的测试用例。

3代码没有任何改动，某个测试却大约每十次执行失败一次。你应该怎么做？

不稳定的测试会侵蚀大家对整个测试套件的信任。修复原因（通常是时序或共享数据问题），或者删除这个测试。

要点

  • 大量快速的单元测试，较少的集成测试，少数几个端到端测试。
  • 追溯矩阵能显示没有测试的需求，以及没有对应需求的测试。
  • 按行为给测试命名，并尽快修复不稳定的测试，否则大家会学会无视红色。
