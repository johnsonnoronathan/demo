# 第 1.1 课: 什么是测试用例？

编写测试用例 · 第 1 章: 基础 · 15 分钟

> 逐个字段构建一个测试用例，再对着真实的登录页面手工执行它。

**学完本课你将能够:**
- 说出测试用例的各个字段及其用途
- 写出足够精确、任何人都能重复执行的测试用例
- 手工执行测试用例并记录结果

## 文字稿: 什么是测试用例？ (2:55)

**0:00 欢迎.** 欢迎学习《编写测试用例》。在第一课里，我们只回答一个问题：测试用例到底是什么？ 学完之后，你将能够读懂测试用例、编写测试用例，并且手工执行它。

**0:15 定义.** 测试用例是一份书面的、可重复的检查。它说的是：在这种情况下，当我做了这些具体操作，应该发生这样的结果。 它有三项任务。第一，锁定一个值得检查的行为。 第二，写得足够具体，团队里任何人执行都能得到相同的结果。 第三，记录结果，让你知道软件是否通过了测试。

**0:43 测试用例的组成.** 我们一起来写一个。被测对象是 Larkspur Books 的登录页面，这是一家小型网上书店。 每个测试用例都有一个 ID 和一个标题。标题写明行为：使用有效的邮箱和密码登录成功。 前置条件描述开始之前的状态。这里是：已经存在一个客户账户。 测试数据列出具体的输入。不写“输入一个有效的邮箱”，而是写出真实的地址和密码。 测试步骤是编号的操作，每行一步，写到新人也能照着做。 预期结果要精确说明应该发生什么。不是“能用”，而是你会看到的页面和提示文字。

**1:28 手工执行.** 现在我们手工执行它。第一步：打开登录页面。 第二步和第三步：按照测试数据，先输入邮箱，再输入密码。 第四步：点击“登录”。 页面显示：欢迎回来，Ada。这和预期结果一致。 于是我们记录实际结果，并把这个测试用例标记为通过。

**1:52 用例失败时.** 测试用例很少单独出现。这里是一次小规模执行，包含三个登录用例。 第二个用例检查错误的密码会被拒绝。它通过了。 第三个用例预期连续失败五次后账户会被锁定。结果没有锁定。这是一次失败，而实际结果准确地告诉开发者哪里出了问题。 测试用例失败并不是坏消息。这正是测试用例在履行职责：赶在顾客之前发现缺陷。

**2:25 小结.** 我们来总结一下。 一个测试用例只检查一个行为，并有 ID 和清晰的标题。 前置条件、测试数据和测试步骤让它可以重复执行。 预期结果在执行之前确定，实际结果在执行之后记录。 接下来，我们会看看好的测试用例和弱的测试用例有什么区别。下面的笔记里有一个可以直接复制的模板。

## 课文

测试用例是对某一个行为的书面、可重复的检查。它写明所处的情境、具体的操作以及你期望的结果，让任何人执行它都能得出相同的结论。

## 字段

| 字段 | 填写内容 |
| --- | --- |
| **ID** | 稳定且唯一的标识，例如 `TC-LOGIN-001`。缺陷报告和测试执行记录都会引用它。 |
| **标题** | 被测的行为，用结果的形式表述：“使用有效的邮箱和密码登录成功。” |
| **前置条件** | 第 1 步之前必须成立的条件：账户、设置、数据、起始页面。 |
| **测试数据** | 具体的输入值。要写 `ada@larkspur.test`，而不是“一个有效的邮箱”。 |
| **测试步骤** | 编号，每步一个操作，具体到新人也能照做。 |
| **预期结果** | 软件正确时你会观察到什么。要在执行*之前*确定。 |
| **实际结果** | 实际发生了什么。在执行过程中填写。 |
| **状态** | 通过（Pass）、失败（Fail）、阻塞（Blocked，无法执行）或未执行（Not run）。 |

## 模板

```text
ID:              TC-<AREA>-<NNN>
Title:           <behavior> when <condition>
Requirement:     REQ-<NN>
Preconditions:   - ...
Test data:       - ...
Steps:           1. ...
                 2. ...
Expected result: ...
Actual result:   (filled in during the run)
Status:          Pass | Fail | Blocked | Not run
```

## 动手试试

为 Larkspur Books 的**退出登录**链接写一个测试用例。它应该结束会话，并把顾客带回首页。对照上面的字段检查你的草稿：一位从没见过这个网站的同事，能不能不问你任何问题就执行它？

> **提示.** **失败是有价值的。** 一个写明了精确实际结果的失败用例（“第 6 次尝试仍被允许；账户未锁定”），已经是半份缺陷报告了。

## Quiz

1. 哪个预期结果写得好？
   a. 登录成功。
   b. 打开账户页面，标题为“欢迎回来，Ada”。
   c. 没有出现错误。
   d. 用户对结果感到满意。
   Answer: b. 它写出了可以观察、可以比对的东西。其他选项都会让两名测试人员得出不同的结论。
2. 预期结果应该在什么时候写？
   a. 执行测试之后，根据看到的情况写
   b. 执行测试之前
   c. 只在测试失败时写
   d. 由开发者在修复缺陷后写
   Answer: b. 如果事后再写，你往往会照着实际发生的情况去描述，缺陷就被当成“预期”放过去了。
3. 第 1 步之前必须已经存在一个客户账户。这应该写在哪个字段？
   a. 测试数据
   b. 测试步骤
   c. 前置条件
   d. 实际结果
   Answer: c. 前置条件描述开始之前系统所处的状态。测试数据列出你要输入或发送的内容。

## 要点

- 一个测试用例只检查一个行为，并有 ID 和清晰的标题。
- 前置条件、测试数据和测试步骤让它可以重复执行。
- 执行前先确定预期结果，执行后记录实际结果。
- 一个写明了精确实际结果的失败用例，已经是半份缺陷报告。
