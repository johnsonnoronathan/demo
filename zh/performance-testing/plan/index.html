性能测试测量什么

延迟、吞吐量和错误：每次性能测试都会报告的三个数字，以及为什么延迟要用百分位数来表示。

学习成果

  • 说出性能测试报告的三个数字，以及每个数字反映了用户的什么体验
  • 读懂 p50、p95 和 p99，并解释为什么平均值会掩盖问题
  • 运行练习应用，完成第一次可重复的测量

概念

  • 延迟是一个分布：p50、p95、p99 · 动画
  • 吞吐量和错误率
  • 只有可重复的测量才有用

要点

  • 延迟是一个请求花费的时间，吞吐量是每秒完成的请求数，错误率是失败请求所占的比例。
  • 延迟是一个分布。要报告百分位数：p50 代表典型请求，p95 和 p99 代表慢速长尾。
  • 平均值把快请求和慢请求混在一起，得到一个没有任何用户真正经历过的数字。不要基于平均值设定预算。
  • 记下你是如何测量的（用户数、时长、接口），这样数字才能被重复和比较。

静态测试与动态测试

性能测试的两大类、各自能发现和不能发现什么，以及测试前如何规划要回答的问题。

学习成果

  • 解释静态性能测试和动态性能测试的区别
  • 为给定的问题挑选仍能回答它的、成本更低的测试
  • 写一份简短的测试计划：问题、预算、风险，以及覆盖它们的测试

概念

  • 静态测试：不运行，只检查 · 动画
  • 动态测试：运行并测量
  • 测试计划从问题开始

要点

  • 静态测试在不运行系统的情况下检查代码、查询、资源和配置。它速度快，每次改动都能运行，但只能发现可能存在的问题。
  • 动态测试在真实流量下运行系统，测量用户的实际感受。它更慢，需要一个环境，但能证明影响有多大。
  • 用静态检查及早发现已知模式，用动态测试确认影响，并发现任何规则都描述不了的问题。
  • 先用问题来规划（“结账能否在 50 个用户下保持 p95 低于 300 ms？”），再为每个问题选择能回答它的最低成本测试。

代码审查：N+1 查询

使用数据库的代码中最常见的性能缺陷：如何通过阅读发现它，以及如何消除它。

学习成果

  • 在代码中识别 N+1 查询模式
  • 用静态检查标记循环中的数据库调用
  • 把 N+1 循环改写为一条带 JOIN 的查询，并验证查询次数

概念

  • N+1 查询模式 · 动画
  • 静态发现：包含查询的循环
  • 修复：JOIN、批量查询和查询次数响应头

要点

  • N+1 指先用一次查询取列表，再为每一项多查一次。代价随列表增长，在快速的本地数据库中很难察觉。
  • 从静态角度看，它表现为循环或 .map 回调中的数据库调用。一条简单的 lint 规则就能抓住大多数情况。
  • 修复方法是用一次查询取回全部数据（JOIN、GROUP BY），或用一次批量查询（WHERE id IN (...)）。
  • 统计每个请求的查询次数。随页面大小增长的查询次数就是 N+1 的特征。

自测

  1. 一位同事想把每晚 4 小时的浸泡测试设为每个拉取请求的必需检查。你会建议怎么做？ 拉取请求上只保留快速的静态门禁（最多再加一个简短的负载测试）。浸泡测试按计划在稳定的环境中定期运行，并对其结果设置告警。
  2. 你的负载测试周一在 CI 中通过，周二在没有任何代码改动的情况下失败了。你首先要做什么？ 重新运行并比较。共享运行器噪声很大；检查失败能否复现、同一台机器上是否运行了其他作业，以及与阈值之间的余量是否太小。
  3. 说出 Larkspur 中一个由静态测试先发现的问题，以及一个只有动态测试才发现的问题。 静态：N+1 循环、全表扫描或过重的资源。动态：推荐接口中的 CPU 热点路径，它不符合任何静态规则。
  4. 怎样的性能发现才是可据以行动的？ 它指出原因及其位置、以用户视角描述并附有测量数字的影响、修复方法，以及别人可以核实的证据。
  5. 发布前一天，验收运行中的 D3 超出上限 20 毫秒。产品负责人要求你把上限提高到 450 毫秒，好让它通过。你怎么做？ 不要为了通过而修改上限。如实报告这次失败。如果发布不能推迟，可以由产品负责人签署一份带有到期日和后续跟进的豁免；修改验收标准本身是另一项决定，从下一次运行开始生效。
  6. 智能体报告说，它修复了你项目里的一个 N+1 问题，现在这个接口只运行 3 条查询。你怎么验收？ 在同一个用户旅程上亲自重新运行同一个检查，把你的数字和它引用的数字对比。然后在本地故意撤销修复，确认新加的门禁会失败，最后像审查其他改动一样审查这个分支再合并。
