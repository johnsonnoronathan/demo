Tests de performance

Apprenez à tester les performances d'une application web sous deux angles. Les tests statiques examinent le code, les requêtes et les ressources sans rien exécuter. Les tests dynamiques font tourner le système, lui envoient du trafic et mesurent ce que ressentent les utilisateurs. Vous pratiquez les deux sur Larkspur Books, une petite librairie en ligne lente à dessein.

Ce que mesure un test de performance

Latence, débit et erreurs : les trois chiffres de tout test de performance, et pourquoi la latence s'exprime en percentiles.

Acquis

  • Name the three numbers a performance test reports and what each says about users
  • Read p50, p95 and p99, and explain why an average hides problems
  • Run the practice app and take a first, repeatable measurement

Concepts

  • Latency as a distribution: p50, p95, p99 · animation
  • Throughput and error rate
  • A measurement is only useful if you can repeat it

Points clés

  • Latency is how long one request takes, throughput is how many complete per second, and the error rate is the share that fail.
  • Latency is a distribution. Report percentiles: p50 for the typical request, p95 and p99 for the slow tail.
  • An average blends fast and slow requests into a number no user experienced. Don't set budgets on averages.
  • Write down how you measured (users, duration, endpoint), so the number can be repeated and compared.

Pratique · 15 min Set up Larkspur and take a first measurement. Get the practice app running and record a baseline for /api/books: query count, p50, p95 and throughput at 10 users.

Tests statiques et dynamiques

Les deux familles de tests de performance, ce que chacune peut ou ne peut pas trouver, et comment préparer les questions avant de tester.

Acquis

  • Explain the difference between static and dynamic performance testing
  • Pick the cheaper test that can still answer a given question
  • Write a short test plan: questions, budgets, risks and the tests that cover them

Concepts

  • Static testing: inspect without running · animation
  • Dynamic testing: run and measure
  • A test plan starts with questions

Points clés

  • Static testing inspects code, queries, assets and configuration without running the system. It is fast and runs on every change, but it can only find likely problems.
  • Dynamic testing runs the system under realistic traffic and measures what users feel. It is slower and needs an environment, but it proves the impact.
  • Use static checks to catch known patterns early, and dynamic tests to confirm impact and find what no rule describes.
  • Plan with questions first ("can checkout take 50 users at p95 under 300 ms?"), then choose the cheapest test that answers each one.

Pratique · 15 min Draft a performance test plan for Larkspur. Write a one-page plan that lists the questions you'll answer about Larkspur, a budget for each, and whether a static or a dynamic test covers it.

Vue d'ensemble : résumé

Le vocabulaire et le plan qui vous serviront pour la suite du cours.

Auto-évaluation

  1. A dashboard shows an average response time of 140 ms. Why isn't that enough to say the endpoint is fast? The average hides the tail. p95 could be several hundred milliseconds, meaning one user in twenty waits much longer. Ask for p95 and p99.
  2. Which family of test would you use to check, on every pull request, that no one adds a 600 KB script to the storefront? A static check: measure the assets against a budget at build time. It takes seconds and needs no running server.
  3. Your static checks all pass. Can you say the app handles 50 users at p95 under 300 ms? No. Static checks find known patterns; only a dynamic test under that load can show the p95 users would see.
  4. What must you record next to a measured p95 so someone else can repeat it? The endpoint, the number of virtual users and the duration, the machine, and the exact command.

Budgets de performance

Se mettre d'accord sur des limites avant de mesurer, puis laisser un contrôle les faire respecter à chaque changement.

Acquis

  • Explain what a performance budget is and who should agree on it
  • Choose budget metrics that can be checked statically and dynamically
  • Run an asset budget check and read its result

Concepts

  • Budgets turn opinions into pass or fail · animation
  • Kinds of budget: quantity, timing, rule-based
  • Where the numbers come from

Points clés

  • A budget is a limit agreed before measuring. It turns "is this fast enough?" into pass or fail.
  • Quantity budgets (KB, requests, queries) can be checked statically on every change. Timing budgets (p95, LCP) need a dynamic test.
  • Base budgets on user needs and competitors, then on today's numbers so they're achievable. Tighten them as you improve.
  • A budget check that fails the build gets fixed. A dashboard that turns red gets ignored.

Revue de code : les requêtes N+1

Le bug de performance le plus courant dans le code qui utilise une base de données, comment le trouver en lisant et comment l'éliminer.

Acquis

  • Recognise the N+1 query pattern in code
  • Use a static check to flag database calls inside loops
  • Rewrite an N+1 loop as a single query with joins, and verify the query count

Concepts

  • The N+1 query pattern · animation
  • Finding it statically: loops that contain queries
  • Fixing it: joins, batching, and the query count header

Points clés

  • N+1 means one query for a list, then one more per item. The cost grows with the list and hides in fast local databases.
  • Statically, it looks like a database call inside a loop or a .map callback. A simple lint rule catches most cases.
  • Fix it by fetching everything in one query (JOIN, GROUP BY) or in one batched query (WHERE id IN (...)).
  • Count queries per request. A count that grows with the page size is the signature of N+1.

Pratique · 20 min Find and remove the N+1 in /api/books. Use the query linter to find the N+1 in the books endpoint, rewrite it as one query, and show the query count drop from 101 to 1 with the same response.

Lire les plans de requête

Demander à la base comment elle exécuterait une requête, sans l'exécuter, et corriger les parcours complets de table avec le bon index.

Acquis

  • Get a query plan from SQLite with EXPLAIN QUERY PLAN
  • Tell a SCAN from a SEARCH, and know when a scan is a problem
  • Design an index for a query's WHERE and ORDER BY, add it as a migration, and confirm the plan changed

Concepts

  • SCAN versus SEARCH · animation
  • Choosing index columns: filter first, then sort
  • Indexes cost writes and space

Points clés

  • EXPLAIN QUERY PLAN shows how the database will run a query, without running it. That makes it a static check.
  • SCAN reads every row of a table; SEARCH uses an index to jump to the matching rows. A SCAN of a large table on a hot path is a bug.
  • Index the columns you filter on first, then the columns you sort by, so the database can skip the sort too.
  • Indexes speed up reads and slow down writes. Add the ones your queries need, not one per column.

Pratique · 20 min Turn two full table scans into index searches. Find the full table scans behind /api/orders and the books page, add indexes in a migration, and confirm both plans and timings improve.

Le poids des ressources

Trouver ce qui alourdit une page en pesant ses fichiers, et la faire tenir dans le budget sans changer ce que voient les utilisateurs.

Acquis

  • Find the heaviest files a page loads and judge whether they're needed
  • Recognise render-blocking scripts in a page's HTML
  • Cut page weight below budget and prove it with the budget check

Concepts

  • Where the page weight goes · animation
  • Render-blocking scripts
  • Right-sizing images

Points clés

  • Weigh what the page actually loads. A few files are usually most of the weight.
  • Ask of each heavy file: is all of it needed, and is it needed now? Libraries often bundle far more than you use.
  • A plain <script> in <head> blocks rendering until it downloads and runs. Use defer, or move it.
  • Serve images at the size they're displayed, compressed sensibly, and give them width and height.

Pratique · 15 min Bring the storefront under budget. Fix the two heaviest assets and the render-blocking scripts in public/index.html until npm run budget passes, without changing what the page shows.

Tests statiques sur votre propre projet

Lancer vous-même les contrôles statiques du cours sur un vrai code, lire les chiffres, fixer les premiers budgets et confier les corrections à un agent.

Acquis

  • Find the equivalent of each of the course's static checks for your own stack
  • Run them yourself on one user journey and record a baseline
  • Turn the baseline into first budgets and one gate
  • Hand a finding to an agent, then verify its fix with the same command

Concepts

  • Four questions, any stack
  • Reading real numbers
  • From baseline to budget

Points clés

  • The four static questions carry over to any stack: how heavy is what we ship, how many queries per request, does each hot query use an index, and what blocks rendering.
  • Run the checks yourself the first time. Reading real output is how you learn what's normal for your codebase, and you're the one who decides what's acceptable.
  • Measure one user journey first, not the whole app. A baseline you can repeat beats a survey you can't.
  • Queries per request that grow with page size, and full scans of large tables on a request path, are findings on any stack.
  • Set first budgets just above today's numbers so the gate passes now and catches the next regression; tighten them as fixes land.
  • The agent proposes commands and writes fixes and gates; you run the checks, read the numbers and approve.

Synthèse du cours

Tout ce que le cours a couvert, au même endroit, et la suite.

Auto-évaluation

  1. A teammate wants to add a nightly 4-hour soak test as a required check on every pull request. What would you suggest instead? Keep pull requests to fast static gates (and at most a short load test). Run the soak test on a schedule against a stable environment, and alert on its results.
  2. Your load test passes in CI on Monday and fails on Tuesday with no code change. What do you do first? Rerun and compare. Shared runners are noisy; check whether the failure reproduces, whether other jobs ran on the same machine, and whether the margin to the threshold is too thin.
  3. Name one problem in Larkspur that only static testing found first, and one that only dynamic testing found. Static: the N+1 loop, the full table scans or the heavy assets. Dynamic: the CPU hot path in recommendations, which matched no static rule.
  4. What makes a performance finding actionable? It names the cause and where it is, the impact in user terms with a measured number, the fix, and the evidence someone can check.
  5. The acceptance run fails D3 by 20 ms the day before a release. The product owner asks you to raise the limit to 450 ms so it passes. What do you do? Don't change the limit to pass the run. Report the failure. If the release can't wait, the product owner can sign a waiver with an expiry date and a follow-up; changing the criterion itself is a separate decision for the next run.
  6. An agent reports that it fixed an N+1 in your project and the endpoint now runs 3 queries. How do you accept that? Rerun the same check yourself, on the same journey, and compare your number with the one it quoted. Then break the fix locally to see the new gate fail, and review the branch before merging.
