Écrire des cas de test

Les fondamentaux du test, en courtes leçons. Découvrez ce qu'est un cas de test et ce qui le rend fiable, choisissez les entrées avec les partitions et les valeurs limites, couvrez les chemins d'erreur, transformez un cas écrit en test automatisé et gardez en bonne santé une suite qui grandit.

Objectifs du cours

  • Lire, écrire et exécuter un cas de test à la main
  • Réécrire des cas vagues pour les rendre précis et reproductibles
  • Choisir les entrées de test avec les classes d'équivalence et les valeurs limites
  • Couvrir les cas négatifs et repérer les trous avec des tables de décision
  • Transformer un cas de test en test automatisé avec Arrange, Act, Assert
  • Organiser une suite avec la pyramide des tests et une matrice de traçabilité

  • De la curiosité pour la façon dont les logiciels cassent

Fondamentaux

Ce qu'est un cas de test, et ce qui distingue un bon cas d'un cas faible. · 30 min

1.115 min▶ 2:56

Qu'est-ce qu'un cas de test ?

Les parties d'un cas de test, construit champ par champ puis exécuté à la main sur une vraie page de connexion.

Acquis

  • Name the fields of a test case and what each is for
  • Write a test case precise enough for anyone to repeat
  • Run a test case by hand and record the result

Points clés

  • A test case checks one behavior, with an ID and a clear title.
  • Preconditions, test data and steps make it repeatable.
  • Decide the expected result before running; record the actual result after.
  • A failed test case with a precise actual result is half a bug report.

Auto-évaluation

  1. Which expected result is written well? The account page opens with the heading “Welcome back, Ada”.. It names something you can observe and compare. The others leave room for two testers to disagree.
  2. When should the expected result be written? Before running the test. If you write it afterwards, you tend to describe whatever happened, and bugs slip through as “expected”.
  3. A customer account must exist before step 1. Which field holds that? Preconditions. Preconditions describe the state of the world before you start. Test data lists the inputs you type or send.
1.215 min▶ 1:55

Bons et mauvais cas de test

Cinq habitudes qui rendent un cas de test fiable, et la forme Given, When, Then qu'adoptent beaucoup d'équipes.

Acquis

  • Spot vague wording in a test case and rewrite it
  • Apply five habits: atomic, independent, repeatable, specific, traceable
  • Write a scenario in Given, When, Then form

Points clés

  • Replace vague words with real values and observable results.
  • Keep each case atomic, independent, repeatable, specific and traceable.
  • Given is the setup, When is the one action, Then is the expected result.

Auto-évaluation

  1. A title reads “Add to cart and checkout and apply coupon”. Which habit does it break? Atomic. Three behaviors in one case means a failure doesn't tell you which one broke. Split it into three cases.
  2. Case B only passes if case A ran first and created an order. What should change? B sets up its own order in its preconditions. Independent cases can run in any order, alone or in parallel. B should create the order it needs.
  3. In Given, When, Then, where does the expected result go? Then. Given is the setup, When is the one action, Then is what you expect to observe.

Partitions et limites

Classes d'équivalence et analyse des valeurs limites : quelques entrées bien choisies au lieu de milliers.

Acquis

  • Divide an input range into equivalence partitions
  • Pick boundary values and their neighbors
  • Turn partitions and boundaries into a compact set of test cases

Points clés

  • Group inputs the software should treat the same way, and test one from each group.
  • Bugs cluster at edges: test each boundary and the value just outside it.
  • An off-by-one comparison is only caught by the exact boundary value.

Auto-évaluation

  1. A field accepts ages 18 to 65. Which set covers all the boundaries? 17, 18, 65, 66. Each edge plus its neighbor just outside: 17 and 18 at the bottom, 65 and 66 at the top.
  2. Why test only one value from the middle of a partition? The software should treat every value in it the same way. That's what makes it an equivalence partition. If 5 works, 6 is very unlikely to behave differently.
  3. The code says qty < 10 but the rule is 1 to 10. Which test catches it? Quantity 10. Only the exact maximum hits the wrong comparison. 5, 0 and 15 give the same answer either way.
2.215 min▶ 1:28

Au-delà du chemin heureux

Cas négatifs, cas extrêmes et tables de décision pour les règles qui se combinent.

Acquis

  • List the usual ways input goes wrong
  • Write negative test cases with clear expected messages
  • Build a decision table and spot gaps in requirements

Points clés

  • Every happy path has unhappy siblings: empty, wrong format, extremes, bad timing.
  • Negative cases check that the software fails gracefully, with a clear message.
  • Decision tables list every combination of conditions and expose unspecified ones.

Auto-évaluation

  1. Which is a negative test case for the email field? ada.larkspur.test shows “Enter a valid email”. It feeds deliberately bad input and checks that the software rejects it clearly.
  2. Three yes/no conditions combine. How many rows can the full decision table have? 8. Each condition doubles the combinations: 2 × 2 × 2 = 8. Some rows may collapse.
  3. A decision table row has no specified outcome. What should you do? Ask the product owner before testing. It's a gap in the requirements. Raising it is part of testing.
2.315 min▶ 2:06

Exploratory testing

Learn without a script: steer a time-boxed session with a charter, keep session notes, and turn what you find into test cases.

Acquis

  • Write a charter that gives an exploratory session one clear mission
  • Run a time-boxed session and keep notes someone else can read
  • Turn findings from a session into bugs, questions and new test cases

Points clés

  • Exploratory testing is designing and running tests at the same time, learning as you go.
  • A charter names a target, the resources you'll use and the information you want: one mission per session.
  • Session notes record what you covered, what you found and what you'd explore next, so the session can be reviewed.
  • Good findings become scripted test cases, so the next run doesn't depend on memory.

Auto-évaluation

  1. Which is the best charter for one exploratory session? Explore the discount code field with expired, misspelled and pasted codes to discover how errors are reported. It names a target, the resources (kinds of codes) and the information wanted. The others give no mission, so nobody can tell when the session is done or what it covered.
  2. Halfway through a session on the discount field, you notice the delivery estimate looks wrong. What should you do? Write it in your notes as an issue or follow-up idea, then return to the charter. The charter keeps the session focused. Noting the side issue means it isn't lost, and it can become the charter for a later session.
  3. Your session found that pasting a code with a trailing space rejects it. What should happen to that finding after the debrief? Report the bug, and add a scripted test case so the behaviour is checked on every run. Exploration finds the problem; a written test case keeps it found. Without one, catching a regression depends on someone happening to explore the same path again.

Du cas de test au test automatisé

Transformer un cas de test écrit en code avec Arrange, Act, Assert, et voir un test aux limites attraper un vrai bug.

Acquis

  • Map a written test case onto Arrange, Act, Assert
  • Write a unit test with a test runner
  • Watch a test fail before trusting it to pass

Points clés

  • The test name is the title, Arrange is the setup, Act is the step, Assert is the expected result.
  • A boundary test turns an off-by-one bug red in milliseconds.
  • See a test fail once before you trust it to pass.

Auto-évaluation

  1. Which part of an automated test holds the expected result? Assert. expect(...).toBe(...) is the expected result, checked automatically.
  2. Why watch a new test fail before making it pass? To prove the test can detect the bug. If the test never goes red, it may not be checking what you think.
  3. applyDiscount(20, "SAVE10") returned 20, but the rule says $20 or more gets 10% off. What's the likely bug? It uses total <= 20 instead of total < 20. Returning early when total <= 20 skips the discount at exactly $20. The boundary test exposes it.
3.215 min▶ 1:42

Organiser une suite de tests

La pyramide des tests, la traçabilité vers les exigences et une suite qui grandit en restant saine.

Acquis

  • Balance a suite with the test pyramid
  • Trace test cases to requirements and find gaps and orphans
  • Keep a suite healthy: names, flaky tests, ownership

Points clés

  • Many fast unit tests, fewer integration tests, a handful of end-to-end tests.
  • A traceability matrix shows requirements with no tests and tests with no requirement.
  • Name tests by behavior and fix flaky tests quickly, or people learn to ignore red.

Auto-évaluation

  1. Where should most of your automated tests sit in the pyramid? Unit. Unit tests are fast and precise, so they make up the wide base.
  2. A requirement has no test cases linked to it. What is that called? A gap. It's a coverage gap. An orphan is the reverse: a test case with no requirement.
  3. A test fails about one run in ten with no code change. What should you do? Find and fix the cause, or remove it. Flaky tests erode trust in the whole suite. Fix the cause (often timing or shared data) or remove the test.
